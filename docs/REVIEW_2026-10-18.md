## 1. Conceptual errors found

### C1 Light head misaligned with the row anchors (fixed)

`LanePixelHead` pooled the backbone map with `AdaptiveAvgPool2d((A, G))`. That spreads the A = 18 anchors evenly
over the **whole** feature map, but the anchors only cover the road band (`row_anchor_range: [0.59, 0.995]`, image
rows 226-381 of 384). The light backbone has a receptive field of about 120 px, so this cannot be learned around.

**Measured** with input gradients (which image rows can change the logits of each anchor):

| anchor (image row) | old head sees rows | contains its row | fixed head sees rows |
|---|---|---|---|
| 0 (y = 226) | 0-77 (sky) | no | 147-285 |
| 5 (y = 272) | 35-173 | no | 195-333 |
| 10 (y = 317) | 147-285 | no | 243-381 |
| 17 (y = 381) | 291-383 | yes | 307-383 |

Consequences for past results (`metrics_and_graphics/metrics/*heldout_mean_std.csv`, 2 seeds):

* lite baseline held-out lane F1 0.22 (4 epochs) / 0.32 (16 epochs) vs UFLD baseline 0.88. Most of that gap is
  the bug, not the model size.
* lite v0.5 jumped to 0.85 and **lite v0.5 static** (no temporal information) to 0.75. The learned "flow" can move
  features vertically by up to 8 cells (128 px), and the ConvGRU's 3x3 convolutions widen the receptive field, so
  both partly repaired the misalignment. The "temporal gain over the lite baseline" was mostly a spatial repair.
  The declared primary pair (v0.5 vs v0.5 static) was the right control, but its absolute values are not usable.
* **Every light-model number obtained before 2026-10-18 must be rerun.** UFLD-family results are unaffected (the
  UFLD head is global, and every anchor sees rows 0-383).

Fix: `AnchorRowPool` (`models/lite.py`) interpolates the feature map at each anchor's own row, then averages into
the G cells. Two constant matrix products, so ONNX/TensorRT export is unchanged (the deploy tests pass).
`model.lite_anchor_rows: aligned` is the new default; `uniform` reproduces the old head, and checkpoints
saved before the fix load as `uniform` automatically (`inference/loading.py`). Parameter counts are identical.
Tests: `tests/test_review_2026_10_18.py`.

**Measured effect** (pilot, `configs/elas_pilot_v2.yaml` protocol: 4 epochs, no HPO, seed 1;
`results/review_lite_aligned_pilot`, compared with the same protocol before the fix, `results/elas_pilot_v2`):

| | val lane F1, epoch 1 / 2 / 3 / 4 | held-out test lane F1 |
|---|---|---|
| lite baseline, old head | 0.005 / 0.056 / 0.092 / 0.115 | 0.218 (2 seeds) |
| **lite baseline, fixed head** | **0.351 / 0.706 / 0.775 / 0.785** | **0.895** |
| lite v0.5, old head | 0.345 / 0.535 / 0.622 / 0.645 | 0.700 (2 seeds) |
| **lite v0.5, fixed head** | 0.783 / 0.787 / 0.799 / 0.812 | **0.933** |
| UFLD baseline (unaffected) | 0.686 / 0.745 / 0.771 / 0.780 | 0.881 (2 seeds) |

One seed and 4 epochs is indicative only. Still, the picture changes completely: with 2.49 M parameters the
light model now matches the 21.8 M-parameter UFLD baseline on the held-out scenes, and the temporal gain of
v0.5 over its own baseline (+0.04) is now a realistic size, not +0.48. That makes the light family the stronger
story for the paper. The full run has to confirm it.

### C2 Which UFLD is the baseline?

`UFLDNet` re-implements the official **v1** `parsingNet` (Qin et al., ECCV 2020). The article says the same (UFLD
is the baseline, and UFLDv2 is cited as related work). You described the baseline as
[UFLDv2](https://github.com/cfzd/Ultra-Fast-Lane-Detection-v2). These are different models:

| | UFLD v1 (code now) | UFLDv2 (TPAMI 2022) |
|---|---|---|
| anchors | row anchors only | row anchors + column anchors (CULane: 72 rows x 200 cells, 81 cols x 100 cells) |
| output | (G+1) classes per (row, lane) | location logits `loc_row`/`loc_col` + separate 2-way existence `exist_row`/`exist_col` |
| loss | focal CE (+ optional structural) | classification + ordinal "mean" (expectation) loss (w = 0.05) + existence |
| head | 1x1 conv to 8 ch, FC 2048 | the same, plus optional LayerNorm (`fc_norm=True`) |
| CULane F1 (R18 / R34) | 68.4 / 72.3 (paper) | 75.0 / 76.0 (README) |

Values from the official repositories and configs (`configs/culane_res18.py`: SGD 0.05, batch 32, 50 epochs,
1600x320 input with `crop_ratio` 0.6). Options:

1. **Keep v1 and say so everywhere** (already true in the article). Scientifically valid, because every temporal
   module is compared with the baseline it extends. A reviewer will ask "why not v2?" The answer: v1's
   single-branch head makes the fusion and the controls exact, and ELAS has only the two ego boundaries, which are
   near-vertical, where row anchors suffice. v2's column anchors exist for side lanes and horizontal lanes.
2. **Add UFLDv2 as a second single-frame baseline** (recommended for an IEEE-level venue): `UFLDv2Net` with hybrid
   anchors, its existence head and mean loss, plus at least one temporal variant on top (ConvGRU is the easiest:
   the fusion acts before the head, so it plugs in unchanged). Cost: about one day of code and tests, then one more
   model pair in the run. On ELAS, expect little gain from the column branch. On CULane and OpenLane, expect the
   published +6 F1.

Do not call the current baseline "UFLDv2" anywhere. That would be a factual error a reviewer can check in five
minutes.

## 2. Points that bias the comparison (not errors, but must be reported)

* **M1 Temporal-consistency term.** `temporal_consistency_loss` regularises the single-frame path of every temporal
  model (`per_frame_logits` on t-1 and t). The baselines never get it. The static control gets exactly 0, because
  its frames are identical. A gain can therefore come from regularisation, not from the past frames. HPO searches
  `lambda_temporal` in [0, 0.05], so 0 is reachable. Report the chosen values, and if the primary pair wins, run
  that pair once with `lambda_temporal = 0`.
* **M2 Early overfitting of warm-started temporal models.** In `results/elas_full/run.log`, `ufld_v02`/`ufld_v03` HPO
  trials peak at epoch 1 (val F1 0.77) and fall to 0.72 by epoch 3, while the val/train focal ratio grows to 2.5-2.9.
  The temporal module starts from a converged baseline and memorises 2,890 frames. `elas_full22` (~2.6x more
  training frames) should help. If not, a lower `lr` for the shared backbone (`lr_backbone_mult`) is the standard
  remedy.
* **M3 Light vs UFLD is not "same model, smaller".** UFLD starts from ImageNet. The light backbone is trained from
  scratch, and 74 % of its 2.49 M parameters are in the head MLP (the backbone is 0.46 M). Report MACs and latency
  as well as parameters, and say the light family is a different design point, not a pruned UFLD.
* **M4 Unit of analysis.** Seeds measure training noise. ELAS frames within a scene are strongly correlated, and the
  test has 3-4 scenes. Add a per-scene table and confidence intervals over scenes. A leave-one-scene-out run of the
  primary pair is the gold standard, if the budget allows.
* **M5 Slot swap at crossings.** ELAS relabels the ego boundaries when the car crosses a line (verified in GRI_S01
  frames 530-540: the old right boundary becomes the new left boundary). A temporal model whose history still
  shows the old assignment is penalised on those frames. They are few (about 1 % of frames), but report F1 on
  lane-change frames separately.

## 4. Light models: improvements and advantages over the baselines

What the light family can honestly claim against UFLD v1/v2:

1. **Cost.** 2.49 M parameters vs 21.8 M (UFLD R18 at 384x512, measured), and no ImageNet dependence. Below about
   3 M parameters, an INT8 engine fits in the L2/SRAM budget of small automotive SoCs, which is the argument for
   Jetson Orin Nano-class targets (latency to be measured, `configs/deploy/`).
2. **Locality is now an advantage, not a bug.** With aligned rows, the head is a row-wise classifier in the sense of
   Yoo et al. 2020 (E2E-LMD): each anchor decides from its own row. That is exactly where temporal fusion should
   help most, because a locally occluded row has no other source of evidence. The UFLD head can hallucinate from
   global context, and may need the past frames less.
3. **Streaming.** The ConvGRU variant carries a single (hidden x h x w) state per stream. At stride 16 that is 64 x
   24 x 32 floats, and no feature window is stored.

Improvements worth trying (in order of expected value / cost):

| Improvement | Why | Cost |
|---|---|---|
| ImageNet-pretrained tiny backbone (MobileNetV3-Small or ResNet-18 trimmed to layer3) | removes the "from scratch" confound (M3) and is the standard light choice | low: swap `LightweightBackbone`, keep the head |
| Shrink the head MLP (`mid*G -> hidden`) with a 1-D conv along the cells | 1.8 M of the 2.49 M parameters sit in the first Linear | low |
| Hybrid row/column anchors as in UFLDv2 | side lanes and curves; makes "UFLDv2-lite" a clean baseline pair | medium |
| Knowledge distillation from the trained UFLD baseline (logit KD on the (G+1) cells) | well-documented gain for small lane models (Hou et al. 2019, SAD) | low-medium |
| Ordinal / expectation loss of UFLDv2 (`mean_loss_w = 0.05`) | sharper sub-cell localisation | low |
| Quantisation-aware training (INT8) | the deployment target | medium |

## 5. Ego lane, lane change, turning, vehicles: can ELAS do it?

| Task | ELAS label | Usable? |
|---|---|---|
| Ego lane (the lane the car follows) | the two annotated boundaries are by definition the ego lane | **yes**: what the models already output (slot 0 / 1) |
| Lateral position in the lane | `laneCenter` (x of the lane centre at the bottom row) | **yes** |
| Lane change with direction | `laneChange` in {-1 left, 0, +1 right}: 8 episodes, 1,083 frames | **yes, for evaluation**; too few to train a classifier |
| Number of adjacent lanes | `laneLeft` / `laneRight` | yes (classification) |
| Lane-marking type | `lmtLeft` / `lmtRight` (8 types) | yes (classification) |
| Crosswalk / road signs, intersection flag | `roadSigns`, `intersection` (446 frames) | yes (frame flags) |
| Turning left/right at an intersection | no label | **no** (only the `intersection` flag) |
| Vehicles | no boxes | **no** |

Sign convention **verified on the data**: every `+1` episode ends with one more lane on the car's left
(`laneLeft` 0 -> 1), so `+1` = change to the **right**.

**Implemented and measured (ground truth lanes).** `tac_ufld/ego.py` computes the ego-lane state per frame (centre,
width, lateral offset in lane widths, heading cue) and runs a streaming `LaneChangeDetector`. A manoeuvre starts on
a sustained drift toward a boundary with a short time to line crossing (TLC), or when a boundary passes under the
camera, and it ends when the car is centred again. `scripts/ego_lane_check.py` on all 22 scenes:

```
events 8, detected 8, direction correct 8, false alarms 0 (in 9.4 min of video),
median delay after the label start 0.85 s, frame F1 left 0.74 / right 0.79
```

The thresholds were set once, by hand, before this run and were not tuned. With 8 events the result shows
feasibility. It is not a benchmark. The same loop now runs on every model's **predicted** lanes during
evaluation (`native_elas_lc_*`, section 8). On the `elas_full22` test scenes, the difference to the line above
is the cost of imperfect lanes, and temporal models should reduce it.

**Starting to turn left/right.** Lane geometry gives an early cue: the lateral speed of the offset and the
far-minus-near heading term. A turn at an intersection usually removes the markings, though. Proper options:
ego-motion from CAN/IMU yaw rate (what production systems use), visual odometry, or a dataset with ego pose. OpenLane
is built on Waymo segments, which carry vehicle pose, so turn and lane-change labels can be **derived** from the
pose (yaw rate, lateral displacement). That is a clean, reproducible labelling route on data you already have.

**Vehicles (VisionPilot).** [VisionPilot](https://github.com/autowarefoundation/vision_pilot) runs three Autoware
models in parallel: **AutoSpeed** detects objects and the *closest in-path object* (CIPO) with a distance,
**AutoSteer** predicts ego-path waypoints, and **AutoDrive** is an end-to-end estimator of distance, in-path
presence and road curvature. A Safety Guardian fuses the outputs into ACC/AEB/FCW/LKAS/LDW. Autoware's separate
EgoLanes model labels the left/right ego lanes and updates them during lane changes. The pages consulted did not
name backbones or training sets. To add vehicle detection here:

* **Data:** ELAS has none. **OpenLane** (already on disk) provides 2-D **CIPO boxes** with an importance level for
  its 1,000 segments, so you get lanes + in-path vehicle on the same frames (Chen et al. 2022). BDD100K gives
  boxes, lanes and drivable area for multi-task training (Yu et al. 2020).
* **Architecture:** either a separate real-time detector (YOLOv10, Wang et al. 2024; RT-DETR, Zhao et al. 2024),
  or a shared backbone with a detection head, as in YOLOP (detection + drivable area + lanes, 23 FPS on a Jetson
  TX2, Wu et al. 2022) and YOLOPv2. For this project the cheapest coherent step: a CIPO head (box + "in my lane")
  on the shared ResNet-18 features, trained on OpenLane. "In my lane" can then be checked geometrically against the
  ego-lane polygon from `ego.py`, which is exactly the CIPO definition.

## 8. Metrics beyond F1 (added 2026-10-18)

F1 alone hides *which* error a model makes. A lane-keeping function suffers more from a phantom lane (false
positive) than from a briefly missing one, and a temporal model may trade one for the other. The evaluator
already computed precision, recall, F1/F2, TP/FP/FN counts, and pixel and anchor P/R/F1. It now adds the
following, and every model gets them in `REPORT.md`, `results.xlsx` and the paired tests:

| Group | Metric (key) | Meaning | Better |
|---|---|---|---|
| lane, per frame | `lane_fp_per_frame_iou50`, `lane_fn_per_frame_iou50` | phantom / missed lanes per frame (counts normalised by test size) | lower |
| | `frames_with_fp_rate_iou50`, `frames_with_fn_rate_iou50` | share of frames with at least one phantom / missed lane | lower |
| | `frame_accuracy_iou50` | share of frames with every lane found and nothing extra | higher |
| anchor (existence) | `anchor_false_alarm_rate` | lane claimed where there is none: FP / (FP + TN), the classic FPR | lower |
| | `anchor_miss_rate` | lane cell missed: the classic FNR (= 1 - existence recall) | lower |
| | `anchor_wrong_position_rate` | lane found but more than 10 px away | lower |
| position | `anchor_mae_px`, `anchor_mae_near_px`, `anchor_mae_far_px` | lateral error in original px where both say "lane"; far = top quarter of the ROI (ELAS near/far protocol) | lower |
| ego lane (ELAS native) | `native_elas_center_err_px`, `native_elas_center_err_pct`, `native_elas_center_coverage` | lane-centre deviation, as in the ELAS paper (% of lane width), and how often both boundaries were found | lower / lower / higher |
| lane change (ELAS native) | `native_elas_lc_event_recall`, `_direction_correct`, `_false_alarms_per_min`, `_median_delay_s`, `_frame_f1_left/right` | `tac_ufld.ego` run on the **predicted** lanes vs the `laneChange` label | see names |
| stability | `jitter_px`, `jitter_p95_px` (already there) | frame-to-frame change of the predicted lane x | lower |

**Measured on the pilot** (held-out test, 2,610 frames, 1 seed, 4 epochs; `results/review_lite_aligned_pilot`):

| metric | lite baseline | lite v0.5 |
|---|---|---|
| lane F1 / precision / recall (IoU 0.5) | 0.895 / 0.895 / 0.895 | 0.933 / 0.933 / 0.933 |
| phantom lanes per frame / missed lanes per frame | 0.209 / 0.209 | 0.134 / 0.134 |
| frame accuracy (all lanes right, nothing extra) | 0.853 | 0.915 |
| anchor false-alarm rate (on 3,048 "no lane" cells) | 0.969 | 0.771 |
| anchor miss rate / wrong-position rate | 0.004 / 0.030 | 0.010 / 0.012 |
| position MAE all / near / far, px | 3.24 / 2.80 / 4.77 | 2.33 / 1.91 / 3.78 |
| lane-centre deviation, px / % of lane width | 4.87 / 1.00 % | 3.28 / 0.69 % |
| jitter, px | 2.68 | 1.68 |
| lane-change false alarms per minute (test has no events) | 0.00 | 1.37 |

Two ELAS properties to state in the paper. (1) Every test frame has two annotated lanes and every model predicts
two, so a miss is a misplaced lane: it counts once as FP and once as FN, and precision = recall = F1. The
per-frame and anchor-level metrics are what separate the error types. (2) Almost every anchor cell holds a lane:
only 3,048 of about 67,000 test cells are "no lane" (lane outside the image or hidden), and both models label
most of them "lane". Row-anchor models extrapolate the lane, which is a known UFLD behaviour. Always report the
false-alarm rate together with its population. The pilot also shows a trade-off that F1 hides: lite v0.5 is
better on every lane and position metric, but its smoother, extrapolated lanes cause lane-change false alarms
(1.4 per minute) where the baseline has none.

Lane-level "true negatives" do not exist in detection (the background is not a countable set), so the FPR/FNR
pair is defined at the anchor cells, where every cell is either lane or no lane. Statistics: the primary Holm
family is unchanged (lane F1 of the declared pairs). Every extra metric is its own exploratory Holm family, so
adding metrics does not dilute the primary test. In the paper, report P, R, FP/frame, FN/frame and position MAE
next to F1, with frame accuracy as the ADAS-facing summary.

## 12. Remaining design risks (decisions, not code bugs)

* **R1 History too short for occlusion.** History = t-2, t-4 at 29.97 FPS = 133 ms. Occlusions by vehicles last
  seconds, which is why the persistent protocol erases most of the gain. Your history ablation shows that steps 5
  and 10 cost nothing on clean frames (test F1 0.859 / 0.858 vs 0.860 for step 2). Before the final run, compare
  step 2 vs 10 under the persistent protocol in a pilot. If step 10 (history 0.67 s) helps, use it in
  `elas_full22`.
* **R2 Recurrent train/deploy mismatch.** The ConvGRU is trained on 3-frame windows from a zero state, but is
  carried for minutes in "carry" deployment, where its state leaves the training distribution. Train recurrent
  variants on longer clips (truncated back-propagation, e.g. T = 8-16), or report the window mode as the deployed
  one.
* **R3 Compute, not only parameters.** Lite baseline 1.99 GMACs vs UFLD 7.12 at 384x512 (**measured**): 8.7x
  fewer parameters, but only 3.6x fewer MACs, because the first full-resolution 3x3 convolutions dominate. On an
  embedded target, MACs and memory traffic set the latency.
* **R4 Lane-change thresholds** were set by hand. For the paper, tune them on the training scenes with events
  (GRI_S01/S02, VIX_S04, VIX_S07, VV_S02, ROD_S03) and report ROD_S01 (2 events, held out in `elas_full22`) as
  the test. Event counts are tiny, so present it as a feasibility demonstration.

## 14. Can a light model reach or beat the state of the art?

Honest answer: **on raw accuracy against the best image detectors, very unlikely; on accuracy per unit of
compute, yes, and that is a publishable claim**, provided it is measured on a public benchmark.

* ELAS has no published deep-learning results, so "state of the art on ELAS" is not a claim a reviewer will
  accept. Use ELAS for the controlled temporal study, the ego-lane results and the lane-change results.
* **OpenLane-V with the RVLD protocol** (already implemented in this repository, uncommitted) is where a light
  temporal model can be compared with published video detectors. Values below are from Tables 2-3 of SIGMA-Lane
  (accepted to ECCV 2026, self-reported):

  | method | F1@0.5 | F1@0.8 | flicker R_F@0.5 | params (M) | GFLOPs |
  |---|---|---|---|---|---|
  | RVLD (ICCV 2023) | 0.825 | 0.566 | 0.014 | - | - |
  | OMR (ECCV 2024) | 0.836 | 0.582 | 0.016 | 7.15 + 3.54 | 54.6 |
  | LaneTCA (TCSVT 2025) | 0.822 | 0.574 | 0.050 | 1.62 + 0.96 | 28.9 |
  | SIGMA-Lane (ECCV 2026) | 0.838 | 0.591 | 0.018 | 3.96 + 0.35 | 27.1 |
  | **lite (this work)** | to measure | | | 2.5-2.8 | ~4 (2 GMACs) |

  With about 7x fewer FLOPs than the lightest of them, a lite temporal model at F1@0.5 of 0.80 or more would
  already be a strong efficiency result; 0.83 or more would match the state of the art.
* On CULane the bar is 81.4 F1 (CLRerNet); UFLDv2-R18 reaches 75.0. Position a 2.5 M-parameter row-anchor model
  against UFLD/UFLDv2 and the efficient detectors (SRLane, CLRKDNet, TwinLiteNet+), not against CLRerNet.

## 15. How to improve the light models with temporal features (ranked)

1. **Temporal shift in the light backbone** (TSM, Lin et al. 2019; online edge version, Lin et al. 2020): shift
   1/8 of the channels from the previous frame. Zero extra parameters and MACs, streaming-friendly (cache one
   slice per layer), shown on a Jetson Nano. It is the best fit for an embedded temporal model. I found no
   published work combining it with row-anchor lane detection (one search, not a systematic review).
2. **Occlusion-aware memory** (the idea of OMR and SIGMA-Lane): gate the ConvGRU write with a per-cell
   "visibility" estimate, e.g. the current frame's existence confidence, so an occluded frame does not contaminate
   the memory. Combine with R1 (longer history) and R2 (longer training clips).
3. **Output-level recursion** (RVLD's idea, almost free with row anchors): feed the previous frame's (G+1) x A x L
   probabilities, shifted by the ego-motion, to the head as a prior.
4. **Ego-motion instead of learned flow**: speed and yaw rate are known in a car (CAN) and in CARLA. Warping the
   history by them is cheaper than the learned flow and cannot "cheat" spatially (C1).
5. **Distillation** from the trained UFLD temporal model into the light student (CLRKDNet shows the gain for
   lanes), plus **INT8 quantisation-aware training** for the embedded target.
6. **Cheaper stem** (R3): a depthwise-separable or stride-4 first block to cut the full-resolution MACs.

## 16. Embedded and simulation path

1. **CARLA closed loop** (CARLA 0.9.16 is installed, see `docs/CARLA.md`): the ego vehicle is steered by
   `ego.lane_keeping` and LDW is logged, in scenarios with occluding traffic and lane changes (CARLA
   ScenarioRunner / OpenSCENARIO). Metrics: lateral deviation RMS, line crossings per km, warnings per km, time to
   first departure. Lane ground truth comes from CARLA itself (`scripts/carla_collect.py`). Test protocols to
   mirror: Euro NCAP Lane Support Systems (LDW, LKA, ELK) and UN R79.
2. **Renode** (Antmicro) simulates microcontroller-class and some application-class SoCs. It is an established
   way to test TensorFlow Lite Micro builds without hardware. Expect **functional** verification (INT8 outputs
   bit-exact with the reference, memory fits), **not** real latency. A 2-GMAC model is far beyond a Cortex-M
   budget. For a realistic target, use a Jetson Orin Nano class board (`configs/deploy/`) with TensorRT, or QEMU
   for Arm Cortex-A functional tests, and measure timing on the real board.
3. **Open-source "professional" stacks**: Autoware with AWSIM, and CARLA + ScenarioRunner with OpenSCENARIO
   scenarios (esmini runs the same OpenSCENARIO files) for repeatable regulatory-style tests.

## 24. TSM robustness and a training-recipe flaw (measured, pilot: 1 seed, 4 epochs)

| held-out test lane F1 | clean | current frame only | persistent | held-out corruptions |
|---|---|---|---|---|
| lite baseline | 0.891 | 0.795 | 0.795 | 0.732 |
| **lite_tsm** | **0.938** | **0.931** | 0.775 | **0.910** |
| lite_tsm_static (control) | 0.931 | 0.858 | **0.858** | 0.762 |

TSM uses time (+0.073 over its static twin with a corrupted current frame, +0.148 with unseen corruptions), but
under a **persistent** corruption it falls below both its static twin and the single-frame baseline. Cause: the
training recipe degrades the current frame only (`current_frame_prob`), so the history is ALWAYS clean in
training and the model learns to trust it unconditionally. New option `data.augmentation.
current_frame_persistent_share` (default 0, earlier runs reproduce exactly): the share of degraded clips in
which the same degradation covers every frame. Recommended for the final run: **0.33**, together with the
persistent robustness protocol as a reported result. Single-frame models and the static controls are
unaffected (one frame), so the current frame's corruption is distributed identically for every model; test
added.
